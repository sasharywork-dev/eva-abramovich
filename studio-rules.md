# Правила вёрстки под Studio (GrapesJS Studio SDK)

Свод техтребований к `index.html`/`css/style.css`, выведенных опытным путём при подключении
сайта к [@grapesjs/studio-sdk](https://app.grapesjs.com/docs-sdk) (файл `studio.html` в копии
`eva-abramovich-editor`). Нарушение любого пункта не ломает сам сайт — он продолжит нормально
работать в браузере, — но что-то в Studio перестаёт редактироваться, показываться в дереве слоёв
или в панели стилей. Связанный документ: [RULES.md](RULES.md) (контент и дизайн-решения).

---

## 1. Единицы измерения

- **Только `rem`.** Никаких `em` — em считается от font-size конкретного элемента, из-за чего
  одно и то же число визуально означает разное в разных местах, и это же путает Style Manager
  редактора. При переводе em → rem пересчитывать через реальный font-size исходного правила
  (`0.02em` при font-size `1.6rem` → `0.032rem`, не `0.02rem`).
- **`line-height` — только в процентах**, не безразмерным числом. `line-height: 1.3` →
  `line-height: 130%`. Работает идентично, но так единообразнее с остальными величинами.
- Эти два правила распространяются в том числе на шорткод `font: вес размер/высота-строки семья`
  — то, что после `/`, тоже переводится в проценты.

## 2. SVG-иконки

- **Только настоящие `<svg>` элементы.** Никогда не оборачивать в `<span>` и не подключать через
  CSS `mask: url(...svg)` на пустом div/span — такой span визуально работает, но остаётся
  бесполезной пустышкой в глазах любого визуального редактора.
- **Никогда не через `::before`/`::after`.** Псевдоэлементы — это сгенерированный CSS-контент,
  а не узлы DOM. Они физически не могут появиться в дереве слоёв НИ ОДНОГО редактора (ни Studio,
  ни Webflow, ни GrapesJS) — это не баг конкретного инструмента, а фундаментальное ограничение.
  Если декоративная иконка нужна редактируемой — превращать `::before`/`::after` в реальный
  дочерний `<svg>` с тем же `position: absolute` и координатами.
- **Раскраска — через `currentColor`, не через фон.** Внутри svg у всех `<path>` `fill`/`stroke`
  должны быть `fill="currentColor"` / `stroke="currentColor"` (никаких зашитых hex/`black`), а
  сам цвет задаётся снаружи через CSS `color: ...` на классе-обёртке. Старая схема
  (`background-color` + `mask: url(...)`) не работает с инлайн-svg и её нужно полностью убирать
  (включая соответствующие `-webkit-mask`/`mask` строки в CSS).
- Если исходный `.svg`-файл использует `fill="none"` на корне (обычно для чисто обводочных
  фигур) — при инлайне это нужно сохранить на новом `<svg>`, иначе путь без явного `fill`
  унаследует чёрную заливку по умолчанию вместо `none`.

## 3. Именование классов — Client-First

- `block_element` (одно подчёркивание) вместо BEM `block__element`.
- Модификаторы — комбо-классом `is-модификатор` вторым классом, а не `block--modifier`.
  Пример: `class="band is-indigo section_epigraph"`, не `class="band band--indigo epigraph"`.
- Секции верхнего уровня — с префиксом `section_имя` (`section_hero`, `section_contact` и т.д.).
- Корневая структура — `page-wrapper` (обёртка всего `<body>`), `main-wrapper` (класс на
  `<main>`). Обеим классам стили не нужны — это просто структурные якоря.
- Никаких однобуквенных/неописательных классов (`.a`, `.h`, `.icon`) — давать осмысленное имя
  по правилу «блок_элемент» (`.topics_answer`, `.contact_row-handle`, `.steps_icon`).

## 4. Адаптивные значения position/size — breakpoint должен совпадать с устройством редактора

Это самое неочевидное правило, вскрытое на примере стрелок-завитушек (`steps_squiggle`):
их `position`/`width`/`height` лежали целиком внутри `@media (min-width: 861px) { ... }`.
Устройства редактора (Desktop/Tablet/Mobile) сопоставляются с CSS-правилами **только когда их
media query совпадает с тем, что генерирует сам редактор** (или когда правило вообще без media
query — тогда оно относится к Desktop/базовому состоянию). Кастомный `861px`-брейкпоинт не
совпадает ни с чем в Device Manager редактора — в результате при выборе элемента на Desktop
панель Style показывала все значения нулями, хотя на самом сайте всё рисовалось верно.

**Правило**: значения, которые должны быть видны/редактируемы на Desktop-вьюпорте в Studio,
обязаны жить в безусловном (без `@media`) правиле. Адаптация под мобильный — только через
`@media (max-width: Npx) { ... }` поверх базового правила (скрыть/переопределить), никогда
наоборот (базовое = mobile-hidden, показ через `min-width`).

## 5. CSS-переменные, `clamp()`, множественный `font-weight` — не трогать в исходнике, но помнить про редактор

Сам `css/style.css` продолжает свободно использовать `var(--x)`, `clamp(min, preferred, max)` и
`font-weight: 400 500` (variable font range) — это нормальный, современный CSS, менять его в
угоду редактору не нужно.

Но: встроенный CSS-парсер GrapesJS/Studio эти конструкции не всегда разбирает и может молча
терять часть правил (шрифты, кнопки — самый частый симптом: «панель стилей пустая» или «шрифт
подменился на системный»). Инструмент подключения (`studio.html`, `editor.html`) отвечает за
это сам — перед тем как передать CSS редактору, гоняет его через `flattenCss()`:
- разворачивает все `var(--x)` в литеральные значения (берёт первое определение переменной по
  файлу, обычно это и есть базовый `:root`; локально-скоупнутые вроде `--topic-pad` на `.topics`
  тоже подхватываются);
- заменяет `clamp(min, preferred, max)` на `preferred`;
- схлопывает `font-weight: 400 500` до `font-weight: 400`.

Если добавляешь новую переменную/`clamp()`/вариативный шрифт в `style.css` — ничего в самом
файле делать не нужно, `flattenCss()` их подхватит автоматически по тем же правилам.

## 6. Как именно подключать CSS к Studio SDK

- **Не вставлять CSS как `<style>`-тег внутрь HTML `component`.** Браузер такой тег применит
  честно (визуально всё будет верно), но внутренняя модель CssComposer, из которой Style
  Manager читает данные для панели, о нём знать не будет — в итоге панель пустая **у любого**
  элемента на странице, не только у отдельных. Это была причина, почему `display: grid` у
  `.contact_grid` не показывался — и не только у него, у всех вообще.
- **Правильно**: передавать CSS через `editor.setStyle(flatCss)` внутри колбэка `onReady`
  (см. п.7) — это настоящий метод GrapesJS, кладёт правила в CssComposer напрямую.
- Google Fonts — отдельным настоящим `<link>` через `canvas: { styles: [googleFontsHref] }` в
  конфиге `createStudioEditor`, не текстом внутри css (иначе у шрифта не резолвятся его
  собственные внутренние `url()`).

## 7. Недокументированные, но реальные детали API Studio SDK

Документация (`app.grapesjs.com/docs-sdk`) на момент проверки (версия пакета `1.2.1`) местами
неточна или неполна — эти детали подтверждены разбором самого файла `index.umd.js`, а не доков:

- Параметр контейнера называется **`root`**, не `container` (в доках показан пример с
  `container`, он не работает — редактор молча не рендерится, `console.error`).
- Поле **`styles`** на странице проекта (`{ name, component, styles }`) в реальном бандле не
  встречается — не использовать, полагаться на `editor.setStyle()` (см. п.6).
- Есть недокументированный колбэк **`onReady(editor)`** — отдаёт настоящий GrapesJS-совместимый
  инстанс редактора (`editor.on(...)`, `editor.getWrapper()`, `editor.setStyle()` и т.д.).
  Есть и `onEditor(editor)` — вызывается раньше, до полной готовности; для наших целей нужен
  именно `onReady`.
- **Лицензия не нужна на localhost** — `license is essential for running the Studio on a public
  domain`, локально работает полностью бесплатно и без ограничений.
- **Дерево слоёв (Navigator/Layers) по умолчанию не показывает классы** — только голый тип тега
  (`Div`, `Header`...). Чинится вручную в `onReady`: обход дерева компонентов
  (`editor.getWrapper()` → рекурсивно `.components().models`) и `comp.set('name', ...)` в формате
  `tag.класс1.класс2`.

## 8. Сохранение (Save) — рабочий рецепт, ставить сразу в новом проекте

Документация утверждает: «by default, your end-user's project data is saved locally in their
browser» — но на практике **без явной настройки `storage` родная кнопка Save молча ничего не
делает**: ни ошибки в консоли, ни сохранения, ни восстановления после `F5`. Проверено вживую —
после клика Save и обычной перезагрузки страницы правки пропадают. Это не баг конкретного билда,
это надо просто сразу настраивать руками при подключении нового проекта.

**Правило**: конфигурировать `storage: { type: 'self', onSave, onLoad }` в конфиге
`createStudioEditor` сразу, не дожидаясь, пока «само заработает»:

```js
const STORAGE_KEY = 'project-name-studio-project'; // свой ключ на каждый проект

createStudioEditor({
  root: '#editor',
  project: { type: 'web', default: { pages: [{ name: 'Главная', component: pageHtml }] } },
  storage: {
    type: 'self',
    autosaveChanges: 1,
    onSave: async ({ project }) => {
      localStorage.setItem(STORAGE_KEY, JSON.stringify(project));
      showToast('Сохранено'); // см. п.10
    },
    onLoad: async () => {
      const raw = localStorage.getItem(STORAGE_KEY);
      if (raw) { restoredFromSave = true; return { project: JSON.parse(raw) }; }
      // ВАЖНО: возвращать объект, не undefined/null — см. следующий пункт
      return {};
    },
  },
  onReady: (editor) => {
    if (!restoredFromSave) editor.setStyle(flatCss); // см. следующий пункт
    // ... nameByClasses и остальное из п.7
  },
});
```

Две конкретные ловушки внутри этого рецепта, обе стоили отдельного отлова:

- **`onLoad` обязан возвращать объект, а не `undefined`/`null`**, даже когда сохранённого
  проекта ещё нет. Внутренний загрузчик Studio делает `result.project` без проверки —
  `return undefined` роняет всё с `TypeError: Cannot read properties of undefined
  (reading 'project')` прямо на старте. Возвращать `{}` в пустом случае, `{ project: ... }`
  в непустом.
- **`editor.setStyle(flatCss)` нельзя вызывать безусловно в `onReady`.** Если он выполняется
  каждый раз (в том числе когда `onLoad` только что восстановил сохранённый проект), он
  затирает сохранённые в Studio правки стилей обратно оригинальным CSS с диска — пользователь
  сохраняет, перезагружает страницу, и правки визуально пропадают (хотя формально Save
  отработал). Нужен флаг `restoredFromSave`, выставляемый внутри `onLoad`, и `setStyle`
  вызывается **только когда его нет** — то есть только на самом первом запуске без
  сохранённого состояния.

`?reset` в адресной строке (`studio.html?reset`) — стирает **только свой** `STORAGE_KEY` из
`localStorage`, не всё хранилище браузера подряд. Нужен, когда осознанно хочешь отбросить
всё, что сохранено в Studio, и перечитать `index.html`/`css/style.css` с диска заново.

## 9. Не городить костыли поверх нативного UI

Когда родной Save не сработал, первая реакция была — навесить свою кнопку/панель поверх
интерфейса Studio (`position: fixed; top: 10px; right: 10px`). Это оказалось неправильным
решением дважды:
1. Кнопка физически перекрыла родные контролы Studio, из-за чего стало невозможно даже
   протестировать/продиагностировать исходную родную кнопку.
2. Это лечило симптом (нет способа сохранить), а не причину (не настроен `storage`) —
   в итоге получались два параллельных, несинхронизированных механизма сохранения.

**Правило**: если что-то в родном UI Studio не работает — сначала чинить причину через
конфиг/API самого SDK (см. п.8), а не перекрывать интерфейс своими элементами. Кастомный UI
поверх Studio — крайняя мера, и если он всё же нужен, размещать его так, чтобы гарантированно
не перекрывать зоны, где может быть родной тулбар (верх экрана) — например, внизу по центру.

## 10. Уведомления — не `alert()`/`confirm()`

Нативные `alert()`/`confirm()` браузера требуют клика «ОК», чтобы продолжить работать со
страницей — раздражают при частых срабатываниях (например, при автосохранении). Использовать
простой самоисчезающий тост (свой `<div>`, фиксированное позиционирование, CSS-transition
на `opacity`, `setTimeout` на скрытие). Пример уже есть в `studio.html` (`#save-toast`,
функция `showToast(text)`) — просто копировать в новый проект и вызывать из `onSave`.

## 11. Псевдоэлементы, которые пока не тронуты

На момент написания в `css/style.css` остаются три легитимных `::after`-стрелки
(`.navbar_menu a[data-cta]::after`, `.btn::after`, `.contact_rows a b::after`, все три через
`arrow-ur.svg`) — это НЕ ошибка и не забытое место: они не были в списке «превратить в svg»,
когда чинились восклицательный знак/подчёркивание в «Как начать». Если понадобится и их сделать
редактируемыми в Studio — правило то же, что в п.2: реальный дочерний `<svg>` вместо `::after`.
